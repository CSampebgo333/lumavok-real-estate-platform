# Database schema

There are **22 application models**, plus Prisma's migration history and Supabase-managed Auth/Storage schemas. Exact column types, defaults and FK actions are in [schema.prisma](../database/schema.prisma); additional PostgreSQL guarantees are in the ordered [migrations](../database/migrations/). SQL is authoritative when Prisma cannot represent a CHECK, partial index, trigger, privilege or cross-schema FK.

## Entities

| Table                            | Important fields and relationships                                                                                                                                                                                                    |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `user`                           | CUID PK; unique email and case-folded email index; role; unique nullable UUID `auth_user_id` FK to `auth.users`; name and preferred-language FK. Legacy password hash remains but is not an active password authority.                |
| `property_developer`             | CUID PK; unique `user_id`; unique stable slug; pending/active status and administrator approval metadata; public business contacts; canonical optional city FK; source-language FK; retained legacy fields and soft deletion.         |

| `city`                           | CUID PK; unique proper name; active flag; country code defaults to BF.                                                                                                                                                                |
| `district`                       | CUID PK; city FK; unique `(city_id,name)` and `(id,city_id)` for composite reference integrity.                                                                                                                                       |
| `feature`                        | CUID PK; unique stable code; source-language FK; retained legacy name/category/icon.                                                                                                                                                  |
| `property_feature`               | Property/feature join with unique pairing and FKs.                                                                                                                                                                                    |
| `property_media`                 | Property FK, provider, legacy URL/public ID or Supabase key, type/order/primary flag; optional asset association for new uploads; unique order per property and partial one-primary index.                                            |
| `storage_asset`                  | UUID PK, seller FK, unique storage key, fixed private bucket, state and timestamps. `(id,state)` is unique; attached new media references `(id,AVAILABLE)`.                                                                           |

| `property_developer_rating`      | Rater/seller FKs; unique pair; score CHECK 1–5; legacy comment/type. Retained without a new rating UI/API promise.                                                                                                                    |
| `notification`                   | Seller FK, event/status enum, read date, link, optional template key/params and retained original text.                                                                                                                               |
| `property_analytics`             | Property FK; unique daily rollup; nonnegative views/clicks/favorites.                                                                                                                                                                 |

| `property_translation`           | Composite PK `(property_id,language_code)`; title, description, publication flag and timestamp; complete nonblank text required for publication.                                                                                      |

Original CUID PKs are not converted to UUIDs. Managed identity and new storage asset IDs use UUIDs where their external relationship warrants it. Existing property price precision remains PostgreSQL decimal; returned decimal strings preserve exact amounts. Timestamps and language-independent values are formatted for the selected language in the interface.

## Integrity beyond Prisma

The migrations add composite FKs for geographic and ownership consistency; report target FKs with mutually consistent CHECK rules; unique case-insensitive emails; nonnegative counters/measurements; bounded ratings and translation text; valid currency and rent-period semantics; media order/primary uniqueness; protected ownership/role/approval fields; and publication requirements for new/changed listings. Existing unknown language/currency metadata is preserved for an explicit reviewed backfill rather than silently guessed.

Translation deletion cascades when its parent is intentionally removed; language references restrict removal while in use. Location and appointment relations prevent orphaning data. Listing deletion is a controlled soft-delete operation. New-media deletion is blocked while any attachment references the asset, including RLS-hidden attachments. Replacing an older FK with a stricter composite FK is documented SQL, not loss of the underlying records.

## Query indexes

Retained indexes cover status, city/district, category, listing type, price, seller and created date. Added indexes support active city/date catalogues; owner/updated listing lists and dashboard previews; seller appointment status/schedule/created queries; buyer viewing history; notification owner/status/date queries; pending seller review; unique favorites and translation lookups; daily analytics; report lookup; and asset owner/date queries. Pagination has deterministic ID tie-breakers.

These indexes are derived from implemented query paths. Production query plans, statistics, data volume and load testing are still needed before claiming a measured capacity target. No premature partitions, search service or cache layer is introduced.

## RLS and privilege matrix

The matrix describes the migrated implementation. Application access runs through the trusted API and its non-owner runtime login; operators verify the effective live grants and policies during adoption. Supabase `anon`/`authenticated` and `service_role` receive no application-table privileges after the security migrations. This does not revoke their managed Auth/Storage service responsibilities.

| Data                                        | Public API scope                                    | Account/seller scope                                                                                            | Administrative scope                           |
| ------------------------------------------- | --------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| Active catalogue and published translations | Read active, non-deleted listings of active sellers | Sellers read/edit their own drafts and exact-language content                                                   | Manage authorized records                      |
| Locations, amenities and language settings  | Read reference data                                 | Read                                                                                                            | Restricted writes                              |
| User account                                | None                                                | Own safe account columns; cannot promote role or read password hashes                                           | Authorized identity/role operations            |
| Seller profile                              | Active public business projection; no account email | Sellers manage their own safe profile fields; approval, verification and ownership remain protected                                                     | Pending review and activation                  |
| Favorites                                   | None                                                | Own records only                                                                                                | Narrow operational access where policy permits |
| Appointments/history                        | None                                                | Buyer sees own viewings; seller sees/manages its property appointments; server-derived owner and initial status | Authorized operational access                  |
| Notifications                               | None                                                | Seller's notifications; read/status changes only                                                                | Authorized operational access                  |
| Media/assets                                | Signed public-listing projection                    | Verified owner attachment/upload; protected deletion lifecycle                                                  | Authorized operational access                  |
| Ratings/reports/analytics                   | Only defined safe API projections                   | RLS restricts writers/targets and protected fields                                                              | Moderation/operational access                  |
| Legacy refresh hashes / migration history   | None                                                | No runtime read/write                                                                                           | Migration/owner operations only                |

Policy predicates, `USING`/`WITH CHECK`, column-level grants and guard triggers work together. A policy alone does not grant table access. Internal SECURITY DEFINER helpers are restricted, have fixed search paths and are not publicly callable. [SECURITY.md](../SECURITY.md) explains the trusted actor-context boundary and remaining risks.
